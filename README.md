# OVENQUILL Soulblade

Серверный плагин для Paper/Purpur 26.2, реализующий легендарный предмет «✦ Клинок душ»: секретный двухэтапный крафт, индивидуальный прогресс до 50 уровня, выпадение голов и безопасное постоянное хранение.

## Требования

- Minecraft / Paper / Purpur 26.2;
- Java 25 или новее;
- SQLite (по умолчанию) либо MariaDB;
- Velocity не обязателен. Для нескольких backend-серверов следует использовать одну MariaDB и уникальный `plugin.server-id`.

Доступность целевой среды проверена: [Purpur 26.2](https://purpurmc.org/download/purpur/26.2), а [Paper требует Java 25 для 26.1+](https://docs.papermc.io/paper/getting-started/). Проект использует официальный новый формат зависимости `paper-api:26.2.build.+`.

## Быстрый старт

1. Соберите проект командой `./gradlew clean test shadowJar` (`gradlew.bat` в Windows) либо возьмите готовый JAR из Releases/Artifacts.
2. Поместите `build/libs/ovenquill-soulblade-1.0.0.jar` в `plugins/` backend-сервера.
3. Запустите сервер. Плагин создаст `config.yml`, `messages.yml`, `recipes.yml`, `mobs.yml` и случайный HMAC-секрет.
4. Обязательно сохраните резервную копию `security.signing-secret`. Его смена делает ранее выданные предметы недействительными.
5. Для сети Velocity переключите `storage.type` на `MARIADB` на каждом backend и укажите одну общую БД.

## Игровая механика

Клинок имеет фиксированный базовый урон 0,5 HP. Критические удары, Strength и чары не усиливают его, при этом стандартная броня, Resistance, absorption, тотемы и отмена урона другими плагинами продолжают работать. Предмет не ломается и не принимает зачарования.

Уровень вычисляется только из авторитетного счётчика БД:

```text
totalKills(L) = floor(1 000 000 × (L - 1)² / 2401)
chance(L) = min(15%, 0,3% × L)
```

Уровень 2 начинается с 416 убийств, 49 — с 959 600, 50 — ровно с 1 000 000. После 50 уровня счётчик продолжает расти. Смерть засчитывается только при непосредственном смертельном ударе мечом. Спавнерные мобы разрешены без лимитов; существа из яиц исключаются. Повторное убийство одного игрока тем же клинком блокируется на 30 минут.

У визер-скелета при таком убийстве удаляется и ванильный череп, но само убийство засчитывается. Looting не влияет на бонусный шанс.

## Секретный крафт

Плагин не регистрирует `ShapedRecipe`: комбинации отсутствуют в серверном реестре и не синхронизируются через стандартную книгу, JEI, REI или EMI. Матрица проверяется только сервером. Просмотр доступен лишь через `/sb recipe` с permission администратора.

Крафт позиционный. Для второго этапа подходит только подписанное Сердце душ; исходный незеритовый меч должен быть целым и незачарованным. UUID регистрируется в БД до выдачи предмета, а повторный клик блокируется.

## Команды

| Команда | Назначение |
|---|---|
| `/sb info` | UUID, уровень, убийства и создатель меча в руке |
| `/sb history` | краткая история меча |
| `/sb recipe` | административный просмотр рецептов |
| `/sb performance` | состояние bounded-очереди хранения |
| `/sb diagnose` | диагностика Secret Crafting |
| `/sb admin give <player>` | зарегистрировать и выдать новый меч |
| `/sb admin setkills <count>` | установить счётчик |
| `/sb admin setlevel <1..50>` | установить точный порог уровня |
| `/sb admin validate` | проверить HMAC и наличие записи БД |
| `/sb admin stats` | число зарегистрированных мечей |
| `/sb admin reload` | перечитать обычные настройки |

Полный список permissions находится в `plugin.yml`; обычным игрокам по умолчанию доступны только использование, info и history.

## Хранение и безопасность

Таблицы создаются автоматически: `blade_instances`, `blade_kill_events`, `player_kill_cooldowns`, `blade_owner_history`, `admin_audit`, `duplicate_conflicts`. Каждое убийство имеет уникальный event UUID; начисление прогресса, PvP cooldown и журнал выполняются одной транзакцией. Для одного клинка используется optimistic revision. Все SQL-операции идут вне игрового потока через ограниченную очередь; при переполнении неподтверждённый прогресс не считается сохранённым.

Предмет содержит тип, UUID, версию формата и HMAC-SHA256. Переименование обычного меча не создаёт Soulblade. БД остаётся авторитетным источником уровня и убийств.

### Резервное копирование

- SQLite: остановите сервер и скопируйте `plugins/OvenquillSoulblade/soulblade.db` вместе с `config.yml`; при работающем сервере используйте штатный SQLite backup/VACUUM INTO, а не обычное копирование WAL-файла.
- MariaDB: используйте `mariadb-dump --single-transaction <database>` и храните копию `config.yml` отдельно.
- Перед миграцией или восстановлением остановите запись со всех backend-серверов. Сначала восстановите БД в отдельную схему, проверьте UUID/revision, затем переключайте серверы.

## Конфигурация голов

Стандартные головы описаны в `mobs.yml`. Для декоративной `PLAYER_HEAD` добавьте Base64-свойство `texture`. Плагин не делает HTTP-запросов во время убийств. Если сущность не настроена, убийство засчитывается, но случайная голова не создаётся.

## Производительность

- событийная архитектура, без сканирования игроков/инвентарей по тикам;
- быстрый выход для обычного оружия;
- 0 синхронных SQL и 0 HTTP-запросов при убийстве;
- ограниченная очередь (`storage.queue-capacity`);
- один worker SQLite или два worker MariaDB;
- частицы/звук создаются только при повышении уровня;
- prepared statements, индексы и транзакции;
- `/sb performance` не запускает тяжёлое профилирование.

Для реальной нагрузки сравнивайте baseline и активные фермы через spark. Цифры TPS/MSPT зависят от железа и состава сервера, поэтому в репозитории не публикуются вымышленные результаты.

## Сборка и тесты

```bash
./gradlew clean test shadowJar
```

Unit-тесты проверяют контрольные пороги уровней, границы миллиона и ограничение шанса 15%. Ручной серверный чек-лист приведён в [docs/TESTING.md](docs/TESTING.md).

## Известные ограничения

- Абсолютно скрыть рецепт после того, как игрок увидел результат или опубликовал комбинацию, невозможно.
- Конфликт физически дублированного предмета нельзя обнаружить, пока копия лежит в неактивном контейнере.
- Этот первый релиз не включает интерактивные команды `backup/recover confirm`; резервирование выполняется средствами выбранной СУБД по инструкции выше.
- Полное нагрузочное профилирование требует отдельного живого Purpur-сервера, набора клиентов и реального окружения плагинов; локальная сборка подтверждает компиляцию и unit-тесты, но не заменяет этот этап приёмки.
- Изменения реквизитов подключения к БД и signing secret требуют полного рестарта, не `/reload`.
